<p>关于"按并发计费"的说法，流传最广的几条几乎都错得差不多：把并发当成端口，把连接当成账号，把不限并发当成随便用。这些误解本身不致命，致命的是签合同时按错误理解估了量，用到第三周才发现账单口径和想象的不一样。下面把五个常见说法逐个拆开，每个都给一个可以自己去核对的判断方法。</p>

<h2>一、五个说法先摆出来对照</h2>
<p>先把误解和实际口径并排放，差距一目了然。表中"实际口径"指多数服务商在订单或技术文档里采用的定义，具体仍以合同为准。</p>
<h3>为什么这些词容易被混用</h3>
<p>端口、连接、并发、账号、会话，这五个词在销售话术里经常互换使用，因为它们听起来都像"同时用几个人"。但在计费系统里，它们的统计对象完全不同，一个是监听入口，一个是 TCP 会话，一个是在飞请求数，一个是身份，一个是保持状态。</p>
<h3>自查的第一步</h3>
<p>翻出你手上的订单或开通邮件，找"并发""连接数""端口数"三个词的原始表述，看它后面跟的单位是人、个还是条。找不到明确表述，就先按最保守的口径估算用量，别按最乐观的。</p>

<h2>二、说法一：并发数等于端口数</h2>
<p>这是最常见的误解。端口是服务端的一个监听入口，一个端口后面可以挂很多条并发请求，只要带宽和连接表撑得住。</p>
<h3>一个端口能带多少并发</h3>
<p>实际取决于三件事：出口带宽、服务端的文件描述符上限、以及目标站点的频率限制。一条 50Mbps 的住宅出口，跑纯文本接口，5 到 20 路并发通常没问题；跑大文件或长连接，可能 3 路就开始排队。</p>
<h3>怎么自己测拐点</h3>
<p>用 <code>ab -n 200 -c 5</code> 或 <code>wrk -t4 -c10 -d30s</code> 逐步加压，记录每档的 P95 延迟与失败率。延迟开始非线性上升的那一档，就是这条线的实际并发上限，与端口数无关。</p>

<h2>三、说法二：连接数就是账号数</h2>
<p>连接是四元组层面的会话，一个账号在浏览器里打开几个标签页、加载几个资源，就会产生几十条连接。把连接数当账号数，估出来的量会大一个数量级。</p>
<h3>连接是怎么被放大的</h3>
<p>一次页面加载会并发拉取 HTML、脚本、样式、接口，现代浏览器对同一域名默认开 6 条左右。再加上长连接的心跳与重连，单账号稳定占用的连接数在 20 到 60 条之间很常见。</p>
<h3>该盯的是并发请求而不是连接</h3>
<p>计费口径若写的是"并发连接"，要问清楚统计的是 TCP 连接峰值还是 HTTP 在飞请求峰值。前者受浏览器行为影响大，后者才更接近业务量。这个问题值得在付款前问一次。</p>

<h3>一个可用的估算式</h3>
<p>并发请求约等于同时在线人数乘以人均在飞请求数。文本对话场景人均在飞请求往往只有 1 到 2 个，所以 10 人团队的实际并发峰值常在 3 到 6 之间，远低于按人数买的直觉。</p>

<h2>四、说法三：不限并发等于随便用</h2>
<p>"不限并发"通常是营销表述，技术上都有限制，只是限制点不在并发数上。真正先撞上的往往是带宽或目标侧的频率。</p>
<h3>三道更硬的墙</h3>
<p>第一道是出口带宽，跑满就打住；第二道是服务端连接表与 CPU，超过就排队；第三道是目标站点的频率限制，这一道最容易被忽略，也最不可控。</p>
<h3>不限并发套餐的适用形态</h3>
<p>适合请求短、峰值分散、可重试的场景。对长连接、大响应体的场景，不限并发反而容易把带宽吃满，导致所有请求一起变慢。买之前先用真实流量跑一天，看峰值形状是否匹配。</p>

<h2>五、说法四与说法五：按并发一定便宜、按账号数算就够</h2>
<p>这两条经常成对出现，逻辑上是同一个错误：用静态数字去套动态流量。</p>
<h3>什么时候按并发更划算</h3>
<p>峰均比高、但峰值持续时间短的业务，按并发买通常更省，因为只需为峰值那一小段付费。反之，流量平稳、全天都在跑的采集类业务，按流量计费往往更可控。</p>
<h3>账号数与峰值的差距</h3>
<p>十个账号不代表十个并发。若成员分布在不同时区、使用时段错开，峰值可能只有 3；若集中在同一小时开会式使用，峰值可能到 8。估量前先统计一周的在线人数曲线，再决定买多少。</p>
<h3>把口径写进订单备注</h3>
<p>付款前用一句话固定定义：并发指同时处于处理中的 HTTP 请求数，统计窗口 5 分钟，取月度第 95 百分位。服务商能接受这句话，说明口径清楚；接受不了，就要留出至少 30% 的余量。住宅出口月费大致 60 至 200 元一条（仅供参考），并发型套餐通常在此之上按档位上浮，多留余量的成本并不高。</p>

<h2>常见问答</h2>
<h3>买了 10 并发，是不是只能 10 个人用？</h3>
<p>答：不是。10 并发指同时在飞的请求数上限，人数可以更多，只要他们的请求在时间上错开。文本对话场景人均占用很低，10 并发常能支撑二三十人的日常使用。</p>
<h3>端口数买多了会浪费吗？</h3>
<p>答：看用途。多端口主要价值在隔离与分流，一号一端口便于绑定和排查。若只是容量问题，加带宽或提并发档位通常比加端口更划算。</p>
<h3>怎么判断服务商说的并发是哪种口径？</h3>
<p>答：直接问统计对象和采样窗口，比如"是 TCP 连接峰值还是 HTTP 在飞请求，取 1 分钟还是 5 分钟第 95 百分位"。答得清楚的，通常计费也更规范。</p>
<h3>超出并发上限会怎样？</h3>
<p>答：多数是排队或返回 429，少数会直接断开连接。表现是延迟陡增而带宽未满，遇到这种情况先降并发，再考虑升档，不要第一反应就换服务商。</p>
